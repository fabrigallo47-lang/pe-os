PE OS — Repository Guide

A typed knowledge graph for private equity deal analysis. Documents go in; a structured, epistemically-typed property graph comes out. Every claim carries its source, its type, and its relationship to every other claim.

What this is

PE OS is a locally-run intelligence layer over deal documents. It extracts factual claims from any document (CIM, QoE report, model, email), labels each claim by epistemic type, links claims to diligence questions, and builds a property graph where contradictions, time-series evolutions, and cross-source challenges surface automatically.

Three non-negotiable design principles:

PrincipleWhat it means in practice
Everything is typedEvery claim is attested / asserted / observed / derived. The system never conflates a seller claim with a QoE finding.
State is derived, never setDeal stage, contradiction count, staleness — all computed from the event log, not from a human-updated field.
Nothing leaves the machineAll computation is local. Model API calls are the only outbound channel and are explicitly listed in the policy table.

Claim schema

Every extracted claim is a JSON object with these fields:

FieldTypeDescription
subjectstringThe company or entity being measured (e.g. "PANTA"). NOT the metric.
metricstringWhat is being measured — "EBITDA", "Revenue", etc.
valuestringNumeric value, or empty for narrative/thesis claims
unitstring"$m", "%", "x", etc.
periodstringTime reference: "FY2025A", "LTM", "Q3 2025"
perimeterstringEconomic boundary: "QoE-normalised", "management-reported", "consolidated"
epistemicenumSee epistemic types below
directionenumsupports / contradicts / context
source_docstringDocument the claim comes from
authorstringParty making the claim — "management", "Big4 Advisory"
statementstringFull natural-language statement of the claim
derivationstringFormula / reasoning (derived claims only)
bears_onstring[]Diligence question IDs this claim is evidence for
topicstringFree-text topic; maps to one of the 8 macro areas

Epistemic types

TypeMeaningTrustExample
attestedQualified third party formally certifiesHighest (3)QoE-confirmed EBITDA
observedDirectly recorded by a third partyHigh (2)Audited revenue from filing
derivedComputed from other stated valuesHigh (2)EBITDA margin = EBITDA / Revenue
assertedSeller or management claim, unverifiedLowest (1)Management's CIM EBITDA figure

The trust hierarchy feeds into automatic edge detection: an attested claim on the same metric as an asserted claim produces both a CONTRADICTS edge and a SUPERSEDES edge (the higher-trust claim displaces the lower).

Graph — node types

Every claim expands into up to 9 nodes. Shared dimensions (same metric across multiple claims, same period, same source) become the same node — this is what enables graph algorithms to find structural patterns across the document set.

claim
The fact itself. Carries value, unit, epistemic type, direction, statement. ID: claim:0001
entity
The company being measured. One node per unique subject. E.g. entity:panta
metric
The KPI axis. Shared across claims. E.g. metric:ebitda
period
Time reference. period:fy2025a, period:ltm
source
Document origin. source:qoe_report, source:cim
perimeter
Economic boundary / definitional scope. Captures what "EBITDA" actually means in context.
area
Macro diligence area. Rendered as background cluster in Graph view.
question
Diligence question node. Claims attach here via BEARS_ON edges.

Graph algorithms

The property graph (tools/graph_store.py) runs on NetworkX. Available via the /analytics endpoint or directly in Python.

from tools.graph_store import DealGraph, graph_path

dg = DealGraph.load(graph_path("panta"))

# PageRank — most structurally central nodes
pr = dg.pagerank()

# Betweenness — bridge nodes between clusters
btwn = dg.betweenness()

# HITS — hubs vs authorities
hubs, authorities = dg.hubs_and_authorities()

# All CONTRADICTS edges with full node data
contras = dg.contradictions()

# Claims that measure a specific metric
claims = dg.claims_sharing_metric("EBITDA")

# Structural path between any two nodes
path = dg.shortest_path("claim:0000", "claim:0006")

# Top-N nodes by PageRank, filtered by type
top = dg.top_by_pagerank(n=10, types={"claim", "metric"})

# Full stats
dg.stats()
# → {"nodes": 38, "edges": 82, "node_types": {"claim": 10, "metric": 6, …}}
ℹ
The graph is persisted at .index/graphs/<deal>.json in NetworkX node-link format after every extraction. Load it any time with DealGraph.load() — no server needed.

Vault structure

The vault is the canonical data store — plain typed markdown, git-backed. The SQLite index is derived and disposable; never treat it as truth.

vault/
  ontology/        ← schemas: claim.md, question.md, decision.md, …
  deals/
    panta/
      deal.md      ← deal metadata (state DERIVED, never manually set)
      questions/   ← diligence questions
      claims/      ← typed claim files
      decisions/   ← IC records, append-only
  entities/        ← companies, people (observed, not maintained)
  library/         ← reusable question-types across deals
  policy/
    policy-table.md  ← every allowed external action
  inbox/           ← artifact drop-zone → run /ingest

.index/
  vault.db         ← SQLite (disposable, rebuild: make index)
  graphs/
    panta.json     ← NetworkX property graph
